# Spec: headless Node.js "linked device" for the Polkadot App (Pi housephone)

Read-only source study, 2026-11-20. Nothing was built or run; the cloned code was treated as untrusted.

**Goal.** A Node.js daemon on a Raspberry Pi that behaves like Polkadot Desktop does as a linked device of the owner's phone:

- it pairs;
- it receives the owner's chats;
- it detects incoming audio call offers and rings;
- it answers, with media handled by a Python **aiortc** process;
- it hangs up;
- second priority, it places outgoing audio calls.

## 1. Pairing as a linked device

### 1.1 What Desktop does

Desktop runs the Rust TrUAPI core as WASM through `@parity/truapi-host` 0.31.0. It calls `createWebWorkerPairingHostRuntime(worker, callbacks, {hostConfig})` (`pdc-pcf/src/aggregates/truapi-runtime/truapiRuntimeUseCase.ts:26-33`).

**Host config** (`pdc-pcf/src/features/product-runtime/feature.tsx` ~40-55):

```ts
host: { name: 'Polkadot Desktop', version, icon, platform: isElectron() ? 'Desktop' : 'Web' },
stack: environment.stack, pairing: { deeplinkScheme: 'polkadotapp' }
```

**Login.** `requestLogin` drives `auth.authStateChanged` through these states: `Pairing{deeplink}` (show it as a QR code), then `Authenticating`, then `Connected{SessionUiInfo}`.

**Afterwards Desktop reads three things:**

- The **chat secret**: `provider.getSessionChatIdentityKey()` (`truapiRuntimeUseCase.ts:251-255`).
- The **device keys**, straight from the core-storage slot `PairingDeviceIdentity` (`pdc-pcf/src/domains/device/$usecase/identity.ts:8,59-64`).
- The **user identity**, from `SessionUiInfo` (`aggregates/p2p-chat/p2pChatUseCase.ts:35-54`).

The flow is **SSO pairing v2** in the core:

- `tua/rust/crates/truapi/src/runtime/sso_request_service/pairing.rs:116-287`. It polls every 2 s, with a 300 s deadline (`:53-65`).
- The pairing identity is **regenerated on every explicit login** (`:135-139`).

### 1.2 Wire format (SSO pairing v2)

Sources: `tua/rust/crates/truapi/src/host_logic/sso/pairing.rs`, `pairing/v2.rs`. Android's mirror is `feature/sso/impl/.../SsoHandshakeProtocol.kt` and `HandshakeOfferScale.kt`.

**Device identity**, generated by the pairing host (`pairing.rs:442-455,529-535`):

- sr25519: a random 32-byte mini secret, then `expand_to_keypair(Ed25519 mode)`, stored as `SecretKey::to_bytes()` = scalar(32) ‖ nonce(32).
- X25519: random.

It is persisted as core-storage slot **`PairingDeviceIdentity`**, 160 bytes (`pairing.rs:57-66`):

```
[0..64)    statement secret (schnorrkel to_bytes: scalar32 ‖ nonce32)
[64..96)   statement public key (sr25519)  = D.stmt
[96..128)  X25519 secret                   = D.encPriv
[128..160) X25519 public                   = D.encPub
```

> **Secret conversion.** `@novasamatech/statement-store`'s prover wants the *Ed25519-expanded* layout. Multiply the scalar by 8: a byte-wise left shift by 3 with carry over bytes 0..31; bytes 32..63 are copied unchanged (`pdc-pcf/src/domains/device/identity/service.ts:38-55`). Then check that the derived public key equals `[64..96)` (`:66-84`).

**Proposal and deeplink** (`pairing.rs:97-102,482-514`; `v2.rs:9-46`):

```
VersionedHandshakeProposal::V2 = 0x01 ‖ device.statement_account_id[32] ‖ device.encryption_public_key[32]
                                 ‖ metadata: Vec<(MetadataKey u8, String)>
MetadataKey: 0 Custom(String) | 1 HostName | 2 HostVersion | 3 HostIcon | 4 PlatformType | 5 PlatformVersion
deeplink = "polkadotapp://pair?handshake=" + lowercase hex (no 0x)
```

`HostName` is always emitted. **It decides whether the phone will device-sync with you (§4.1).**

**Answer** (posted by the phone; `pairing.rs:108-118,193-212,517-527`):

```
topic1 = khash(key = D.stmt, msg = D.encPub ‖ "topic")          // subscribe matchAll:[topic1]
data   = VersionedHandshakeResponse::V2 = 0x01 ‖ Bytes() encrypted_message ‖ ephemeral_pub[32]
shared = X25519(D.encPriv, ephemeral_pub);  key = HKDF-SHA256(salt=∅, ikm=shared, info=∅, L=32)
encrypted_message = nonce[12] ‖ ChaCha20-Poly1305 ct ‖ tag[16]
plaintext v2::EncryptedResponse:
  0x00 Pending(0x00 AllowanceAllocation)
  0x01 Success{ identity_account_id[32], root_account_id[32], identity_chat_private_key[32],
                sso_enc_pub_key[32], device_enc_pub_key[32], root_entropy_source[32] }
  0x02 Failed(String)
```

- The phone posts Pending, then Success, each with a fresh ephemeral key (Android `RealRegisterDeviceUseCase.kt:40-46`; iOS `PolkadotHandshakeSender.swift:85-105`).
- The **signer of the Success statement** is the phone's statement account (`peer_statement_account_id`, `sso_request_service/pairing.rs:384`). On Android it equals `identity_account_id` (`RealSsoHandshakeUseCase.kt:54,76`).

**What a chat/call device must keep:**

- `A.id = identity_account_id`
- `A.chatPriv = identity_chat_private_key`, with `A.chatPub = X25519.pub(A.chatPriv)`
- `D.*` from `PairingDeviceIdentity`
- the phone's `{stmt = Success signer, encPub = device_enc_pub_key}`, which is the first device-sync peer (§4)

`root_*` and `sso_enc_pub_key` are only needed for SSO *requests* to the phone, such as signing. Chat and calls do not use them.

### 1.4 What the phone does: announcement, allowance, checks

Android `feature/sso/impl/.../domain/devices/RealRegisterDeviceUseCase.kt:31-63`, in order:

1. `respondToOffer(AllowanceAllocation)`.
2. `slotAllocator.allocate(deviceStatementAccountId, INCREASE, High)`. **The phone pays**: it submits `Resources.set_statement_store_account(period, seq, target = D.stmt)` with its personhood slot collection (`RealStatementStoreSlotAllocator.kt:155-188`). Period = `floor(unix/86400)`.
3. Persist the SSO session as ACTIVE.
4. `respondToOffer(Success)`.
5. `broadcastDeviceAdded(D.stmt, D.encPub)`.

iOS does the same (`PolkadotHandshakeSender.swift:141-151`).

**Allowance:**

- Per slot it is `AccountsApiAllowance = 2 statements / 500 KiB` (`research-chain.md:85`). The slot expires about 2-3 days after its period.
- Android **renews** all slots, including the device's, from a WorkManager job every hour (`StatementStoreSlotRenewalWorker.kt:44-60`). **If the phone does not run for more than about a day, the Pi stops being able to submit** [inferred].
- **Budget:** the Pi can hold only about 2 live statements at a time. Newer, higher-priority submissions evict older ones (`accountFull{min_expiry}` handling, `SS/submit/retry.js`). Calls fit, because each session reuses one request channel. Do not ack chat (§2.6) [verify the real allowance on the owner's network].

**Announcement:**

- Android posts chat content `deviceAdded{stmt, encPub}` (index 17) to every multi-device contact over the contact's **main** session (`RealBroadcastDeviceLifecycleUseCase.kt:23-36`; `RealContactChatSession.kt:121-125`).
- `ContactDeviceFanOutService.kt:47-63` re-announces all our devices to newly established contacts. The source is `RealOurDevicesProvider`: the phone plus every ACTIVE SSO session, with **no host filter**.
- The Pi does **not** announce itself.
- The announcement is not identity-signed. Trust comes from the encrypted channel (`identityChannel.ts:47`).

**Checks:** no attestation, platform allowlist or host-type check on pairing. The metadata is only displayed (`PairRequestViewModel.kt`). `HostPlatform::Cli` is a first-class value (`truapi/src/v01/system.rs:99`).

## 2. Chat transport

### 2.0 Primitives (exact)

| Name | Definition | Source |
|---|---|---|
| `khash(key, msg)` | `blake2b(msg, {dkLen: 32, key})`, i.e. BLAKE2b-256 keyed | `SS/crypto.js:21-23` |
| `X25519(priv, pub)` | RFC 7748 (`@noble/curves` `x25519.getSharedSecret`); throws on small-order points | `SS/session/codec/envelope.js:68` |
| `Enc(S)` | key = `HKDF-SHA256(ikm=S, salt=b"", info=b"", L=32)`; `encrypt(p) = nonce(12, random) ‖ ChaCha20-Poly1305(key, nonce).encrypt(p)` (ciphertext ‖ 16-byte tag); no AAD | `SS/session/encyption.js:7-23` |
| `AeadRaw(K)` | same as `Enc`, but the 32-byte `K` is used **directly** as the ChaCha20-Poly1305 key, with no HKDF | `SS/session/codec/envelope.js:55-63` |
| `SessionId(S, A, B)` | `khash(S, "session" ‖ A.accountId(32) ‖ B.accountId(32) ‖ pin(A) ‖ pin(B))`, where `pin(x) = "/"` when there is no pin, else `"/" ‖ utf8(pin)`. Chat never uses pins, so the suffix is **`"//"`** | `SS/model/session.js:5-18` |
| `RequestChannel(topic)` | `khash(topic, "request")` | `SS/session/codec/outgoingBody.js:23-25` |
| `ResponseChannel(topic)` | `khash(topic, "response")` | `:26-28` |

### 2.1 SCALE notation used below

- `str` = compact(len) ‖ utf8 bytes.
- `Bytes()` = compact(len) ‖ bytes.
- `Bytes(N)` = N raw bytes.
- `Vec<T>` = compact(count) ‖ items.
- `Option<T>` = `00` or `01 ‖ T`.
- `u8`, `u16`, `u32`, `i32`, `u64` are little-endian.
- An enum is a 1-byte index followed by the payload.

### 2.2 The statement (Substrate Statement Store on the **People** chain)

Desktop's statement store adapter is a polkadot-api client on the **People chain** (`pdc-pcf/src/domains/application/statement-store/service.ts:46-61`; `createPapiStatementStoreAdapter(lazyClient)`).

| JSON-RPC method | Use |
|---|---|
| `statement_submit(hexEncodedStatement)` | submit |
| `statement_subscribeStatement(filter)` | subscribe; filter is `{matchAll:[hex32…]}`, `{matchAny:[hex32…]}` or `"any"`; events are `{event:"newStatements", data:{statements:[hex…], remaining?}}`; unsubscribe is `statement_unsubscribeStatement` |

Sources: `SDKS/api.js:1-9`, `SDKS/statement-sdk.js:7-64`.

- A "query" is a subscribe that is closed when `remaining` reaches 0 (`statement-sdk.js:9-32`).
- Submit results are `new`/`known` (ok), `rejected{reason: dataTooLarge | channelPriorityTooLow{min_expiry} | accountFull{min_expiry} | storeFull | noAllowance}`, or `invalid{noProof | badProof | encodingTooLarge | alreadyExpired}` (`SS/adapter/rpc.js:85-127`).
- The live endpoints and allowance rules are in `research-chain.md`: Paseo People, para 1004.

**Statement encoding** (`SDKS/codec/codec.js:3-72`): `Vec<Field>`, with fields strictly in ascending index order.

| Field idx | Name | Type |
|---|---|---|
| 0 | proof | enum: `0 sr25519{signature[64], signer[32]}`, `1 ed25519{…}`, `2 ecdsa{sig[65], signer[33]}`, `3 onChain{who[32], blockHash[32], event u64}` |
| 1 | decryptionKey | [32] (unused by chat) |
| 2 | expiry | u64 |
| 3 | channel | [32] |
| 4..7 | topic1..topic4 | [32] each (chat uses exactly one topic) |
| 8 | data | `Bytes()` |

**Signing** (`SDKS/signer.js:5-20`): sign the encoding of the statement **without** the proof field and **without** the outer compact length prefix of the `Vec`. Then insert the `proof` field (index 0) first.

- The signer is the **device statement account** (sr25519), with a 64-byte Ed25519-expanded secret, through `@polkadot-labs/schnorrkel-wasm` (`SS/substrateSr25519.js`, `SS/session/statementProver.js:31-37`).
- Receivers verify the signature against the embedded signer only. Sender identity is implied by the ability to derive the topic and keys (`SS/session/codec/decoder.js:50-58`).

**Expiry / priority** (`SS/submit/allocator.js:1-35`): `expiry = (0xFFFFFFFF << 32) | priority`.

- `priority = max(prev + 1, now_secs − 1763164800)`. The constant is the priority epoch, 2025-11-15T00:00:00Z.
- On `channelPriorityTooLow` / `accountFull`, raise the floor to `min_expiry` and retry (`SS/submit/retry.js`).
- The store keeps **one statement per (signer, channel)**. A newer one supersedes the older.

### 2.3 Keys a chat device needs

| Key | Origin |
|---|---|
| `A.id` | owner identity sr25519 public key, 32 bytes |
| `A.chatPriv` / `A.chatPub` | owner identity chat X25519 key pair; the private half is **shared to every linked device at pairing** |
| `D.stmt` / `D.stmtSecret` | this device's statement account (sr25519) |
| `D.encPriv` / `D.encPub` | this device's X25519 key |
| For each contact `B` | `B.id` (32), `B.chatPub` (X25519, 32), and **roster** `B.devices = [{stmt[32], encPub[32]}…]` |

Where these come from: §1 (own keys) and §4 (contacts).

### 2.4 The two channels per contact

#### (a) Device-level "main" session, multi-device

Built with `createMultiDeviceSession` (`SS/session/multiDeviceSession.js:28-61`; used by `pdc-pcf/src/domains/chat/p2p/chatSessionV2.ts:119-135`).

**Outgoing** (what we publish to `B`):

```
K_out    = X25519(D.encPriv, B.chatPub)
topicOut = SessionId(K_out, D.stmt, B.id)            // "session" ‖ D.stmt ‖ B.id ‖ "//"
request statement : channel = RequestChannel(topicOut), topics=[topicOut], data = Enc(K_out).encrypt(SD)
response statement: channel = ResponseChannel(topicOut), same topic/enc
```

**Incoming**: one topic **per contact device** `B'` in `B.devices`. Subscribe to all of them with a single `matchAny` (`SS/session/codec/incomingTopics.js:33-69`).

```
K_in(B')    = X25519(A.chatPriv, B'.encPub)            // == X25519(B'.encPriv, A.chatPub)
topicIn(B') = SessionId(K_in, B'.stmt, A.id)           // "session" ‖ B'.stmt ‖ A.id ‖ "//"
outer decrypt with Enc(K_in(B'))
```

> Consequence: **all of the owner's devices listen on the same incoming topics.** They are keyed by the *identity* chat key and the *identity* account, and every linked device has both. What differs per device is only the inner envelope slot. **You cannot compute these topics without the contact's device roster** (`B'.stmt`, `B'.encPub`).

`SD` is the **StatementData** enum (`SS/session/scale/statementData.js:26-69`):

```
0 request       { requestId: str, data: Vec<Bytes()> }        // single-device form
1 response      { requestId: str, responseCode: u8 }          // 0 success, 1 decryptionFailed, 2 decodingFailed, 255 unknown
2 multiRequest  { encryptedRequest: Bytes(), devicesInfo: Vec<RequestDeviceInfo> }
3 multiResponse { encryptedResponse: Bytes(), devicesInfo: Vec<RequestDeviceInfo> }
RequestDeviceInfo = { statementAccountId: [u8;32], encryptedKey: Bytes() }
```

**Multi-device envelope** (`SS/session/codec/envelope.js:69-114`):

```
oneShot  = random 32 bytes
encryptedRequest = AeadRaw(oneShot).encrypt( SCALE(Request{requestId, data}) )      // nonce(12) ‖ ct ‖ tag
for each recipient device R:  encryptedKey = Enc(X25519(sender.encPriv, R.encPub)).encrypt(oneShot)
```

**To read a peer's statement as device `D`:**

1. Outer-decrypt with `Enc(K_in(B'))`.
2. Decode `SD`.
3. Find the `devicesInfo` entry where `statementAccountId == D.stmt`; if none, the statement is not for us.
4. Recover `oneShot = Enc(X25519(D.encPriv, B'.encPub)).decrypt(encryptedKey)`.
5. Decrypt `Request = AeadRaw(oneShot).decrypt(encryptedRequest)`.

Every `data[i]` is one SCALE `ChatMessage` (§2.5).

**Batching and acks** (`SS/session/core.js`, `SS/session/stateMachine.js`):

- A sender has at most one live outgoing batch. Each new message re-submits the **whole unacked batch** under a fresh `requestId` (nanoid, 21 characters) on the same request channel. This replaces the previous statement.
- The receiver answers `response{requestId, success}` on **its own** outgoing topic's response channel. The response is wrapped `multiResponse` for **all** of the sender's devices.
- **Any one** of the recipient's devices acking clears the sender's batch (`stateMachine.js` `responseReceived`).
- On start, the session queries `matchAll:[topicOut]` (our own last statements) and `matchAny: incoming topics`. It restores and re-delivers an unanswered peer request (`core.js:330-372`).
- Max statement size used: `DEFAULT_MAX_REQUEST_SIZE = 498 KiB` minus 168 bytes of overhead (`core.js:31,47`).

#### (b) Identity-level channel, single-device form

Built with `createSession` (`pdc-pcf/src/domains/chat/p2p/identityChannel.ts:62-76`, `SS/session/session.js:18-37`). It carries only bootstrap and roster content: `deviceChatAccepted`, `deviceAdded`, `deviceRemoved`, and legacy `chatAccepted` (`session-transport/service.ts:356-399`).

```
K_id     = X25519(A.chatPriv, B.chatPub)
topicOut = SessionId(K_id, A.id, B.id)      topicIn = SessionId(K_id, B.id, A.id)
data     = Enc(K_id).encrypt(SD request/response)    // tags 0/1, no envelope
```

Statements are still signed by the *device* statement key. The identity key never signs (`identityChannel.ts:47`).

#### Incoming chat **requests** from strangers

These are a third mechanism (`pdc-pcf/src/domains/chat/p2p/requests/*`). The Pi does **not** need them: it serves the owner's existing contacts.


Index 19 is defined at Android `feature/chats/transport-protocol/.../scale/ChatMessageStatementContent.kt:133-139`.

- A decoder that does not consume 19 correctly mis-reads a whole batch, or a device-sync `Messages` entity.
- Variants 8-11 and 16 must also be fully consumed.

**Attachments** (`HC/codec/attachment.js`): `FileVariant = enum{0 p2pMixnet{identifier: Bytes(), claimTicket: Bytes(), nodeEndpoint: enum{0 wssUrl{url: str}}, meta: FileMeta}}`.

- File bytes live on a **HOP relay**, not in Bulletin.
- A claim is **one-shot**. Desktop deliberately never downloads, because claiming would deny the phone (`pdc-pcf/src/domains/chat/p2p/README.md:21-24`). **The Pi must not claim attachments either.**
- Text is inline. **Nothing is fetched from Bulletin for chat.**

**Message IDs.** Desktop uses `nanoid(12)` (`chatSessionV2.ts:175`). Android uses a UUID string for call offers (`RealCallController.kt:31`). Treat the ID as an opaque string.

### 2.6 How a linked device receives the owner's chats (procedure)

For each contact `B`, with `B.chatPub` and a non-empty `B.devices`:

1. Open the main session (§2.4a) and the identity channel (§2.4b).
2. On `deviceAdded` / `deviceRemoved`, from either channel, update `B.devices`. That recomputes the incoming topics (`managerV2Factory.ts:1063-1081`, `peerRoster.ts`).
   - Android sends roster changes on the **main** session.
   - Desktop also accepts them on the identity channel.
3. Decode every message. Messages are de-duplicated by `messageId` (`chatSessionV2.ts:137-157`).

Desktop refuses to start a session when `B.devices` is empty (`managerV2Factory.ts:964-968`).

**Recommendation for the Pi: listen, do not ack ordinary chat.**

- Desktop acks every decoded request (`chatSessionV2.ts:170-172`, `identityChannel.ts:80-85`).
- Because *any* sibling's ack clears the sender's batch, an ack from the Pi can make an offline phone miss messages.
- Desktop compensates by pushing its messages to the phone over device sync. A receive-only Pi would not.
- So run the Pi's sessions with **no responder**, which means `subscribe()` without `respondToRequests()`. Only send your own requests: answer, candidates, closed.

The sender keeps re-posting its batch until the phone acks. That is normal.

§4 covers where each contact's `B.chatPub` and `B.devices` come from.

## 3. Call signalling

### 3.1 The chat message types used for calls

Desktop maps these at `pdc-pcf/src/domains/chat/p2p/session-transport/service.ts:228-345`.

| Signal | Wire variant (§2.5) | Payload |
|---|---|---|
| **offer** | `8 dataChannelOffer{sdp, purpose}` | `sdp` = SCALE `MinimalSetup` (§3.2); `purpose` 0 = AUDIO_CALL. **The offer's `ChatMessage.messageId` is the call id (`offerId`).** |
| **answer** | `9 dataChannelAnswer{offerMessageId, sdp}` | `sdp` = SCALE `MinimalSetup` (type ANSWER) |
| **ICE** | `10 dataChannelIceCandidate{offerMessageId, sdp}` | `sdp` = SCALE **`Vec<MinimalCandidate>`**, *not* a MinimalSetup (`pdc-pcf/src/shared/peer-channel/sdpCoder.ts:66-85`) |
| **hangup / decline / busy** | `11 dataChannelClosed{offerMessageId}` | none |

Notes:

- There is **no separate "busy" or "answered elsewhere" message.**
  - Android answers a second offer while in a call with `dataChannelClosed`. That is `declineWhenBusyIntent` → `declineOffer` (`tua/hosts/android/feature/calls/impl/.../RealCallController.kt:54-62`, `CallService.kt:330-334`, `RealExternalCallSignaling.kt:106-111`).
  - Decline and end both send `dataChannelClosed` (`CallService.kt:322-340`; Desktop reducer `domains/chat/calls/session/service.ts:104-109`).
- **"Answered elsewhere"** is *inferred* by Desktop:
  - Desktop sees an `answer` or `closed` for the offer id in the session's message list that it did not publish itself (`features/call/ui/BridgeEndpointBinding.tsx:212-236`; `domains/chat/calls/service.ts:46-54`).
  - On a sibling, a sibling's own outgoing `answer` can only arrive through **device sync** (§4). The Pi cannot decrypt the phone's outgoing topic, which is keyed by the phone's `encPriv` and `B.chatPub`.
  - Desktop then closes silently. It sends **no** `closed`, because that would kill the sibling's call (`calls/session/service.ts:197-207`).
  - Desktop HEAD does not run device sync (§4.1). In practice its ringing therefore stops only on the caller's `closed`.
  - **Pi heuristic** [inferred]: an Android caller starts trickling ICE only *after* it has an answer (`InitiatorConnection.kt:64-79`). So a `dataChannelIceCandidate` for the offer id that arrives while the Pi is still ringing means another device answered. Stop ringing.
  - This does not hold for Desktop callers, which trickle before any answer (`BridgeEndpointBinding.tsx:163-171`).
- **Ringable** means an incoming offer with no `answer`/`closed` referencing it (`domains/chat/calls/service.ts:23-40`).
  - iOS additionally ignores offers older than **30 s** by message timestamp (`pic/polkadot-app/Modules/ChatCall/Service/RealCallCoordinator.swift:27-28,117-125`).
  - Android gates only on "no incoming `dataChannelClosed` for this offer" (`RealIncomingCallGate.kt:16-28`).
  - **Pi rule:** ring iff the message is incoming, has purpose AUDIO_CALL (VIDEO may also be answered audio-only, see §3.5), satisfies `now − timestamp ≤ 30 s`, and no `closed` has been seen for it.
- There are **no ring timeouts** in Desktop or Android code [checked: none found]. Use your own: stop ringing after about 60 s or on `closed`.

### 3.2 `MinimalSetup` (exact)

Sources: `pdc-pcf/src/shared/peer-channel/signaling.ts:12-80`, Android `tools/media-connection/impl/.../models/MinimalSetup.kt`, `signaling/SdpCoder.kt`.

```
MinimalSetup = {
  sdpType:        u8 enum   0 OFFER, 1 ANSWER
  sessionId:      compact   (SCALE compact BigInt; from SDP "o=- <sessionId> <version> ...")
  sessionVersion: compact
  iceUFrag:       str       (a=ice-ufrag)
  icePwd:         str       (a=ice-pwd)
  fingerprint:    Bytes()   (raw SHA-256 digest = 32 bytes; from "a=fingerprint:sha-256 AA:BB:...")
  candidates:     Vec<MinimalCandidate>    (first batch gathered; may be empty)
}
MinimalCandidate = {
  foundation:    str
  priority:      i32 (LE)
  transportType: u8 enum   0 TCP, 1 UDP
  address:       enum      0 Ipv4([u8;4] in network order), 1 Ipv6(8 × u16 **little-endian** = 16 bytes)
  port:          u16 (LE)
  candidateType: u8 enum   0 HOST, 1 SRFLX, 2 RELAY, 3 PRFLX
}
```

**Encode, SDP → MinimalSetup** (`sdpCoder.ts:100-151`; Android `SdpCoder.kt:82-131`):

- Take the `a=ice-ufrag`, `a=ice-pwd` and `a=fingerprint` values, and the `o=` 2nd and 3rd tokens.
- `sdpType` = OFFER iff `a=setup:actpass`, else ANSWER.
- The fingerprint is the hex after the first space, colons removed.

> **aiortc gotcha.** aiortc emits **three** fingerprint lines: sha-256, sha-384 and sha-512 (`aiortc/src/aiortc/rtcdtlstransport.py:45-49,171-182`). Desktop's and Android's parsers keep the **last** line seen. Your encoder must explicitly pick the `sha-256` line and put its 32 bytes on the wire. The receiver always labels the bytes `sha-256` (`sdpCoder.ts:168-172`).

**Decode, MinimalSetup → SDP.** This template must match **byte for byte in structure** (`sdpCoder.ts:176-196`; Android `SdpCoder.kt:181-210`):

```
v=0\r\n
o=- {sessionId} {sessionVersion} IN IP4 0.0.0.0\r\n
s=-\r\n
t=0 0\r\n
m=application 9 UDP/DTLS/SCTP webrtc-datachannel\r\n
c=IN IP4 0.0.0.0\r\n
a=ice-ufrag:{ufrag}\r\n
a=ice-pwd:{pwd}\r\n
a=fingerprint:sha-256 {HEX:UPPER:COLON}\r\n
a=setup:{OFFER→actpass | ANSWER→active}\r\n
a=mid:0\r\n
a=sctp-port:5000\r\n
```

Desktop uses CRLF; Android uses LF. Both work. Keep the trailing newline.

- **The answerer must therefore be the DTLS client (`active`).** aiortc's answer is `active` by default (`rtcpeerconnection.py:614-617`), so it matches.
- When the Pi is the offerer, aiortc offers `actpass`, and libwebrtc answers `active`. That also matches.

**Candidate ↔ SDP line** (`iceCandidate.ts:83-127`; Android `SdpCoder.kt:137-179`):

- Decode: `candidate:{foundation} 1 {udp|tcp} {priority} {addr} {port} typ {host|srflx|relay|prflx}`, with `sdpMid="0"` and `sdpMLineIndex=0`.
- Dropped on encode:
  - candidates whose address is not an IP (mDNS `.local`);
  - `raddr`/`rport`, `tcptype` and `generation`.
- Component is always 1.
- iOS additionally drops TCP host candidates (`pic/.../ConnectionCandidateFiltering.swift:16-20`).

**Trickle batches.** Batch up to 4 candidates or 500 ms, whichever comes first (`shared/peer-channel/iceBatching.ts:19-32`; Android `PeerChannelConnection.kt:228-251`).

- The **first batch is embedded** in the offer or answer `MinimalSetup.candidates`. Later batches go out as `dataChannelIceCandidate` while the data channel is not yet open.
- Android sends candidates gathered *after* the data channel opens **over the data channel** as `PeerConnectionSignal.candidates` (`PeerChannelConnection.kt:233-240`).
- An Android *caller* starts trickling only **after** it has received an answer (`InitiatorConnection.kt:61-79`).

### 3.3 Which devices an offer is addressed to

An offer is an ordinary main-session chat message. It is wrapped for **every device in the sender's roster of the callee**: `recipients: () => peerRoster.current()` (`SS/session/multiDeviceSession.js:51`).

- If the phone has fanned out the Pi as a device (§1), the caller's offer has a slot for the Pi, and the Pi rings in parallel with the phone and Desktop.
- The Pi's answer, ICE and closed messages are wrapped for **every device of the caller**.
- The caller (Android) applies the **first** `dataChannelAnswer` whose `offerMessageId` matches (`RealExternalCallSignaling.kt:78-93`). It filters ICE only by `offerMessageId` (`:63-76`).
- The caller does **not** send `closed` to the losing devices. **The owner's phone keeps ringing after the Pi answers.** It stops only when the caller later sends `dataChannelClosed`, at hangup, or when the user dismisses it. Android stops ringing only on an *incoming* `closed` (`CallSessionManager.kt:109-116`). This is a UX limitation of the protocol, not something the Pi can fix.

### 3.4 Exact message sequence: incoming audio call, Pi answers

Roles: caller `B` (Android, iOS or Desktop) is the **initiator**; the Pi is the **acceptor**.

**Phase 1: data channel over the statement store**

1. `B` → all of `A`'s devices: `dataChannelOffer{sdp = MinimalSetup(OFFER, …, first ≤4 candidates), purpose = AUDIO_CALL}`. Its `messageId` is the `offerId`.
   - Android creates the data channel with label `"dataChannel"`; Desktop uses `"call"`. The label is irrelevant.
   - Desktop (`callPeerConnection.ts:90`) and Android (`PeerChannelConnection.kt:130-134`) set `iceCandidatePoolSize = 8`.
2. The Pi rings. **Do not** create the answer yet. Desktop applies the remote offer immediately but answers only on accept (`features/call/runtime/callSession.ts:200-216`, `:118-132`).
3. The user picks up. The Python side:
   - (a) Rebuild the SDP from the template, and **inline the offer's candidates as `a=candidate:` lines** in the m-section. This is safer with aiortc than `addIceCandidate` before ICE starts [verify].
   - (b) `setRemoteDescription(offer)`.
   - (c) `createAnswer` and `setLocalDescription`. aiortc gathers **all** candidates here, so there is no trickle.
   - (d) Encode `MinimalSetup(ANSWER)` from the local SDP, using the sha-256 fingerprint and every `a=candidate` line (UDP, IPv4/IPv6).
4. Pi → `B`: `dataChannelAnswer{offerMessageId = offerId, sdp}`.
   - Optionally also send the candidates as one `dataChannelIceCandidate` frame. Not needed, because aiortc has no trickle.
5. `B` → Pi: more `dataChannelIceCandidate{offerId, Vec<MinimalCandidate>}` frames. Apply them with `addIceCandidate(sdpMid="0")`. Ignore frames for other offer ids.
6. ICE connects, then DTLS (Pi = client), then SCTP. `B`'s data channel opens on the Pi (`datachannel` event).

**Phase 2: media renegotiation over the data channel**

Sources: `features/call/runtime/mediaRenegotiation.ts:66-141`; Android `InitiatorConnection.kt:88-102`, `AcceptorConnection.kt:91-106`.

Every data channel frame is binary SCALE:

```
DataChannelMessage = { id: str, data: Bytes() }        // dataChannelEnvelope.ts:9-12; Android DataChannelMessage.kt
use-case ids:
  "webrtc_renegotiation_internal_use_case" → PeerConnectionSignal
  "webrtc_media_state_use_case"            → MediaStateSignal
  "webrtc_upgrade_consent_use_case"        → UpgradeConsentSignal (Desktop↔Desktop only; ignore)
  "device-sync"                            → device sync (§4), not used on call channels
PeerConnectionSignal = enum { 0 offer(str full SDP), 1 answer(str full SDP),
                              2 candidates(Vec<{ sdp: str, sdpMLineIndex: u32, sdpMid: Option<str> }>) }
MediaStateSignal     = enum { 0 cameraEnabled(bool), 1 microphoneEnabled(bool) }
UpgradeConsentSignal = enum { 0 request, 1 accept, 2 decline }
```

Sources: `peerConnectionSignal.ts:15-25`, `mediaState.ts:11-16`, `upgradeConsent.ts:13-19`. Android sends frames as binary (`DataChannelMessaging.kt`, `DataChannel.Buffer(…, true)`).

7. **Initiator `B`** adds local media and sends `offer(full SDP)` on the renegotiation use case.
   - Android always uses `MediaConfiguration.AudioVideo(initialCameraEnabled = withVideo)`. **Even an audio call's media offer carries an audio *and* a video m-line**, with the video track disabled and H264 preferred (`CallSessionManager.kt:55-67`, `PeerChannelConnection.kt:253-276`).
   - iOS also negotiates a recv-only video transceiver without a camera (`TransceiverConfigStrategy.swift:39-46`).
   - Desktop sends audio only.
   - The SDP is BUNDLEd with mid 0 (application) first. Media reuses the phase-1 ICE/DTLS transport, so normally no new candidates are needed (`mediaRenegotiation.ts:126-129`).
8. **The Pi** (aiortc):
   - (a) `setRemoteDescription(offer)`. aiortc creates recvonly transceivers for audio and video, and bundles them onto the SCTP transport (`rtcpeerconnection.py:921-1077`).
   - (b) `addTrack(micTrack)`. This reuses the audio transceiver and sets it to sendrecv (`:480-505`).
   - (c) Set the video transceiver's `direction = "inactive"`. It is a settable property (`rtcrtptransceiver.py:68-71`). This avoids decoding video on the Pi. `recvonly` also works.
   - (d) `createAnswer` and `setLocalDescription`.
   - (e) Send `answer(full SDP)` on the renegotiation use case.
   - aiortc main has a test for exactly this "data channel first, then add audio by renegotiation" flow: `tests/test_rtcpeerconnection.py:3957` `test_connect_datachannel_then_audio` [verify against libwebrtc peers].
9. If `B` sends `candidates` over the data channel, apply each with its `sdpMid`/`sdpMLineIndex`. The Pi never needs to send any, because aiortc puts all candidates in its SDP.
10. Media flows (Opus). Optionally send `microphoneEnabled(bool)` on mute.

**Hangup**

11. If either side hangs up, it sends chat `dataChannelClosed{offerMessageId = offerId}` over the statement store. **There is no data-channel close signal** (`peerConnectionSignal.ts:8-9`).
    - On receiving it, close the PeerConnection.
    - Treat RTCPeerConnection `failed`/`closed` as the end too. Desktop also treats `disconnected` as failure (`callSession.ts:273-281`).
    - Android tolerates transient states after first connect (`CallSessionManager.kt:136-147`).

**Pi decline or busy.** Recommended: **send nothing**, only stop ringing locally.

- A `closed` would end the call for the caller, so the phone could no longer answer.
- This deliberately differs from Desktop and Android, which send `closed`.

### 3.5 Outgoing call from the Pi (initiator)

1. Pick a fresh `offerId`. The offer's chat `messageId` *is* the offer id: Android uses `messageId = offerId`, a UUID (`RealExternalCallSignaling.kt:32-39`).
2. aiortc:
   - `RTCConfiguration(iceServers, bundlePolicy=MAX_BUNDLE)` is recommended;
   - `createDataChannel("call")`, then `createOffer` and `setLocalDescription`;
   - encode `MinimalSetup(OFFER)`, using sha-256 and all candidates.
3. Send `dataChannelOffer{sdp, purpose: AUDIO_CALL}` on `B`'s main session.
   - Wake the callee's phone with a VoIP push (§3.7). Without it, an iOS callee whose app is suspended will not ring.
4. Wait for the first `dataChannelAnswer` with `offerMessageId == offerId`. Rebuild the SDP from the template, inlining its candidates, then `setRemoteDescription(answer)`. Apply later `dataChannelIceCandidate` frames.
5. When the data channel opens:
   - `addTrack(mic)`, then `createOffer` and `setLocalDescription`;
   - send `PeerConnectionSignal.offer(full SDP)`, then await `answer` and `setRemoteDescription`.
   - Android's acceptor tries to add a video track. Since the offer has no video m-line, its answer stays audio-only [inferred: libwebrtc Unified Plan semantics].
6. Hang up with `dataChannelClosed{offerId}`. Receiving `dataChannelClosed{offerId}` before an answer means declined or busy.

### 3.6 Codecs and audio-only

- **Audio.** The media SDP is plain libwebrtc (Android, iOS) or Chromium (Desktop). Opus/48000/2 is first. aiortc supports Opus, PCMU, PCMA and G722.
- **Video.** Android prefers H264 (`PREFERRED_VIDEO_CODEC = "H264"`, `PeerChannelConnection.kt:54`); VP8 is also offered [inferred].
- **Audio-only is supported:**
  - `purpose = AUDIO_CALL` exists on the wire;
  - Desktop and Desktop↔mobile calls work with audio only;
  - the Pi answers video m-lines as `inactive`.
  - An incoming `VIDEO_CALL` can be answered the same way: inactive video, no camera.

## 4. Device sync, and where contact knowledge comes from

### 4.1 Headline facts

1. **Without contact rosters, a linked device cannot receive anything.**
   - Incoming topics and the per-device unwrap both need each contact device's `{stmt, encPub}` (§2.4a).
   - The sender's encryption public key is **not** carried in the statement.
   - For contacts that already exist at pairing time, the only bootstrap is **device sync**: `ChatsAdded` gives identity ids, and the `Messages` rows `deviceAdded`/`deviceChatAccepted` give the device rosters.
2. **The phone device-syncs only with hosts whose pairing `HostName` is exactly `"Polkadot Desktop"`.**
   - Android: `feature/device-sync/impl/.../RealDeviceSyncCoordinator.kt:97,100` has `takeIf { peer.name == SYNCABLE_HOST_NAME }` with `SYNCABLE_HOST_NAME = "Polkadot Desktop"`.
   - iOS: `pic/polkadot-app/Modules/Chat/Model/LocalDevice.swift:39-41` has `supportsDeviceSyncSession { hostName == "Polkadot Desktop" }`.
   - **A Pi pairing host must advertise `HostName = "Polkadot Desktop"`, or it never gets contacts.** This impersonates Desktop's host label: an interop and policy risk.
   - The roster fan-out to contacts has no such filter (§1.4). Contacts *will* address the Pi either way.
3. **Desktop HEAD does not run device sync.**
   - `pdc-pcf/src/bootstrap.ts:157-166` reads: "TODO(truapi): re-wire device-sync to the core's session identity…".
   - `domains/device-sync/*` is complete but has no callers.
   - Android (`DeviceSyncEngine`, `DeviceSyncRunner`, `SyncScale`) is therefore the authoritative peer. Desktop↔phone sync interop at HEAD is unverified.
4. Mobile treats pairing as complete without sync: `SyncDeviceUseCase` is an 800 ms stub (`RealSyncDeviceUseCase.kt:4-14`).

### 4.2 Device-session pipe: statement-store signalling between the Pi and the phone

Source: `pdc-pcf/src/domains/device-session/*`.

**Inputs:** ours `D.encPriv`, `D.stmt`; the phone's `P.encPub` (Success `device_enc_pub_key`) and `P.stmt` (Success signer).

```
S        = X25519(D.encPriv, P.encPub)
topicOut = SessionId(S, D.stmt, P.stmt)      topicIn = SessionId(S, P.stmt, D.stmt)    // "session"‖a‖b‖"//"
channels = khash(topicOut,"request") / khash(topicOut,"response");  data = Enc(S).encrypt(...)
SignalingStatementData = enum { 0 Request{ requestId: str, messages: Vec<Bytes()> },
                                1 Response{ requestId: str, responseCode: u8 } }       // schemas.ts:20-35
each message = SyncSignalingEnvelope{ offerId: str(UUID),
     message: enum{ 0 Reconnected, 1 Offer{sdp: Bytes()=MinimalSetup}, 2 Answer{sdp: Bytes()=MinimalSetup},
                    3 Candidates{candidates: Bytes()=Vec<MinimalCandidate>} } }     // shared/peer-channel/signaling.ts:99-126
```

**Rules:**

- Ack **every** inbound Request with `Response{requestId, 0}`, duplicates included. Without the ack, Android retries forever (`device-session/$usecase/session.ts:11-12,56-203`).
- Every Request carries the full unacked batch. Dedupe by `requestId`.
- **Roles:** compare `D.stmt` and `P.stmt` as unsigned bytes. The **smaller is the initiator** (`device-sync/orchestrator.ts:56-66`; Android `DeviceSyncEngine.kt:188-191`). `D.stmt` is random, so implement both roles.
- **Offer IDs:**
  - The initiator mints `offerId`; the acceptor answers with the same id.
  - Drop Answers and Candidates whose `offerId` does not match.
  - A new Offer `offerId` resets the attempt.
  - `Reconnected(offerId)` means dispose and respawn (`signaler.ts:196-300`).
- **Timers:** handshake 30 s, respawn 5 s (`device-sync/constants.ts`); Android loops every ~35 s (`DeviceSyncEngine.kt:51-53`).
- Android caps own-device-session statements at 2 KiB (`DevicesSessionManager.kt:50`). Keep frames small.
- The SDP uses the **same MinimalSetup template** as calls (§3.2), data channel only.

### 4.3 Sync data channel

**WebRTC:** data channel only. The initiator creates the channel: Desktop labels it `"sync"`, Android `"dataChannel"`. Use the same ICE config as calls.

**Frames:** `DataChannelMessage{id:"device-sync", data}`, binary. Source: `device-sync/schemas.ts:1-92`; identical to Android `SyncScale.kt`.

```
SyncMessage  = enum { 0 Update(SyncUpdate), 1 Ack{ id: u32 } }
SyncUpdate   = { id: u32, entities: Vec<SyncEntity>, timePoint: u64 (ms) }
SyncEntity   = enum { 0 Devices(Vec<LocalDevice>), 1 ChatsAdded(Vec<ChatId>), 2 ChatsRemoved(Vec<ChatId>),
                      3 Messages(Vec<LocalMessage>) }
LocalDevice  = { statementAccountId[32], encryptionPublicKey[32], status: enum{0 ACTIVE}, lastUpdate: u64 }
ChatId       = enum { 0 Contact([u8;32] identity accountId) }
LocalMessage = { remote: ChatMessage (§2.5), peerId[32] (contact identity id),
                 status: enum{ 0 Outgoing(enum{0 NEW,1 SENT,2 DELIVERED}), 1 Incoming(enum{0 NEW,1 SEEN}) },
                 order: u64 }
```

**What the phone sends on first connect.** The checkpoint starts at 0, so it sends everything (Android `SyncEntityCollector.kt:35-82`):

- `Devices`: our siblings, including the Pi.
- `ChatsAdded`: **all established multi-device contacts** (`DeviceSyncFilter.kt:9-12`).
- `ChatsRemoved`.
- `Messages`: **all** messages. This includes each contact's `deviceAdded`/`deviceChatAccepted` rows, `token` rows (push tokens) and **old call signals**.
- Chunking: 60 KiB per update; all chunks are sent first, then the phone waits for acks (30 s each); the checkpoint advances only when everything is acked (`DeviceSyncRunner.kt`).

**Receiver obligations:**

- Ack every `Update.id`. Re-ack duplicates. Do not ack if apply failed (Desktop `syncStateMachine.ts:204-224`).
- Ignore inbound `Devices`.

**Apply rules** (Desktop `applier.ts`):

- **`ChatsAdded`:** resolve the contact's chat key and username from chain (§4.4). **Retry on failure.** Desktop skips without retry; that is gap G2.
- **`Messages`:** in `order`. For `deviceAdded`, `deviceChatAccepted` and `deviceRemoved` rows **with `status = Incoming`**, upsert or remove a device in `peerId`'s roster, deduped by `stmt`.
  - Keep the roster independent of whether the contact has resolved. Desktop's G1 drops it.
- **Never ring on synced call rows.**
- Synced *outgoing* `dataChannelAnswer`/`dataChannelClosed` rows for a live offer mean "answered elsewhere" (§3.1).
- The Pi may send **no** Updates. That is allowed [inferred].

### 4.4 Contact identity from chain (`Resources.Consumers`)

- **Chain and storage:** People chain, pallet `Resources`, `StorageMap<Blake2_128Concat, AccountId32, ConsumerInfo>`. Key: `twox128("Resources") ‖ twox128("Consumers") ‖ blake2_128(id) ‖ id` (`src/indiv/pallets/resources/src/lib.rs:321-323`).
- **Value:** `ConsumerInfo{ identifier_key: [u8;65], full_username: Option<Username>, lite_username: Username, credibility: enum{0 Lite, 1 Person{alias[32], last_update u64, demoted bool}} }` (`pallets/resources/src/types.rs:88-110`).
- **Decoding:** `identifier_key` = `0x00 ‖ X25519 chat pub[32] ‖ padding[32]`. So `B.chatPub = identifier_key[1..33]` (`pdc-pcf/src/domains/network/identity/schemas.ts:7-23`, `service.ts:49-57`).
- Desktop reads it with papi `Resources.Consumers.getValues` (`network/identity/gateway.ts:24-54`).
- There is **no device roster on chain.**

### 4.5 Minimum for "receive calls"

| Need | Without device sync? |
|---|---|
| `A.chatPriv`, `D.*` | yes, from pairing |
| `B.id` for each contact | **no**: `ChatsAdded` |
| `B.chatPub` | chain lookup by `B.id` |
| `B.devices` | **no**: synced `deviceAdded` rows; afterwards live `deviceAdded` on the main or identity session |

**Minimum sync implementation:**

- the device-session pipe, both roles;
- a data-channel-only aiortc peer;
- the receive-only `SyncMessage` applier with acks, handling `ChatsAdded` and `Messages` device rows.

New contacts the owner adds later arrive through further sync rounds. The phone's runner fires on local DB changes (`LocalSyncTrigger.kt`). So **keep sync running permanently.**

### 5.1 Minimal module set for "receive an audio call and ring"

### 5.2 Things that are impossible or blocked for a third-party client

1. **Device-sync gate on `HostName == "Polkadot Desktop"`** (phone side, §4.1).
   - Technically trivial to satisfy, since there is no attestation. But it is impersonation of the Desktop label, and it could change in any app release.
   - Without it, the Pi has **no contact rosters**, so it cannot decode any offer, even though contacts address it.
   - This is the main "soft-blocker".
2. **The App's TURN relay** (`/api/v1/turn/issue`) needs a Play Integrity or App Attest JWT. Unavailable. Bring your own TURN.
3. **Statement allowance** is paid and **renewed only by the phone**, hourly while it runs.
   - The Pi cannot renew it: renewal needs the owner's personhood slot proof.
   - Budget: about 2 statements per slot [verify]. If the phone is off for more than about a day, the Pi goes mute (it can still *receive*).
4. **Identity sr25519 key** stays on the phone. It is not needed for chat or calls; it would only be needed for SSO-signed actions.
5. **"Answered elsewhere" and multi-ring.**
   - The caller never cancels the losing devices. When the Pi answers, the owner's phone keeps ringing until hangup.
   - The Pi learns of a phone answer only via synced outgoing rows, or the ICE heuristic.
6. **Attachments** are one-shot HOP claims. The Pi must not download them, or the phone loses them.
7. **Interop drift:**
   - Desktop's own device sync is dormant at HEAD.
   - `@parity/truapi-host` field names changed between 0.31.0 and HEAD.
   - host-chat 0.12 lacks Android's index 19.
   - Pin versions and test against the owner's actual phone build.
8. **Background push** for the Pi is not needed: it is always online. No backend registration is required for receiving.

### 5.3 Verdict

**Feasible, with no cryptographic or attestation barrier on the receive path.** Every key a linked device needs is delivered by the phone at pairing or derivable, and the wire formats are fully specified above. The chat crypto can be imported from Apache-licensed npm packages.

Feasibility hinges on two non-technical points:

- (a) presenting `HostName = "Polkadot Desktop"`, so the phone device-syncs contacts and rosters to the Pi;
- (b) the phone staying in use to renew the Pi's statement allowance.

The highest technical risk is aiortc's in-band renegotiation against libwebrtc's audio-plus-video re-offer (§3.4 step 8). Prototype that first.

**Alternative**, if (a) is unacceptable: give the Pi **its own identity** and make it a *contact* of the owner (`truapi-host-cli` `signing-host`/`attest`/`register-name`). It then reuses §2-§3 unchanged. It needs no device sync and no owner's chat secret. The cost is that callers must call the Pi's own identity.
